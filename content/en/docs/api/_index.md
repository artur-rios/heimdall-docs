The Heimdall API is the ASP.NET Core service that holds Heimdall's data and enforces its rules. It
answers one question for many client systems at once, *who is this caller, and what are they allowed
to do?*, while keeping each client system's identities isolated from every other's inside its own
scope. This section is its detailed documentation: what the endpoints are, how the paths that matter
behave end to end, how to run it, and the specification it is built from.

For what Heimdall is and how its parts fit together, start with the
[Overview]({{< relref "/docs/overview" >}}) and the [Architecture]({{< relref "/docs/architecture" >}}).
To run the API, see [Installation]({{< relref "/docs/installation" >}}).

## Endpoints and the OpenAPI document

| Page | What it covers |
| --- | --- |
| [API reference](reference/) | Every endpoint, the role that may call it, and the use case it implements. |
| [API explorer](explorer/) | Swagger UI over the published OpenAPI document. It is read-only: it shows each operation's request and response shapes but does not send requests. |
| [OpenAPI document](../../api/openapi/heimdall.json) | The OpenAPI document itself, as raw JSON. |

The OpenAPI document is generated from the API's controllers and is the complete list of operations.
The reference page is the prose map of it: when the two disagree, the OpenAPI document is right.

## Flows

The [flows](flows/) are sequence diagrams of the paths worth tracing end to end: the ones that cross
services, branch on stored state, or deliberately answer the same way down several paths. There is
one for [login](flows/login/), [two-factor authentication](flows/two-factor/),
[Google Sign-In](flows/google-sign-in/), [person onboarding](flows/person-onboarding/),
[password recovery](flows/password-recovery/), [scope permission claims](flows/scope-permission-claims/),
[audit logging](flows/audit-logging/) and [application authentication](flows/application-authentication/).

## Specification

The [requirements](requirements/) are the specification: the vision, the system requirements, the use
cases, the technology stack, testing, workflow and operations, and the data-protection documents that
the LGPD and the GDPR call for. Every feature traces back to a numbered requirement (`FR-…`,
`NFR-…`) and a use case (`UC-…`), and the other pages cite those identifiers wherever a design
decision came from one.

## Changes and contributing

The notable changes in each release are in the
[CHANGELOG](https://github.com/artur-rios/heimdall-api/blob/main/CHANGELOG.md). How to build from
source, run the test suites, author migrations, regenerate the OpenAPI document, branch and release
is in [CONTRIBUTING](https://github.com/artur-rios/heimdall-api/blob/main/CONTRIBUTING.md). Both live
in the repository and are not rendered on this site.
